# 사용자 인터뷰 → UI 제안 → 구현

이미 답한 내용은 반복해서 묻지 않는다. 설치 경로나 MCP 유무를 사용자 디자인 질문에 섞지 않는다. 대화 언어를 따른다.

## 첫 질문: 최대 세 묶음

1. **목적과 대상**: 어떤 사이트인가요? 주 사용자는 누구이며 방문 후 무엇을 하길 바라나요? (구매 / 가입 / 예약 / 정보 탐색 / 업무 처리)
2. **디자인풍**: 어떤 느낌이 어울리나요? (정돈되고 신뢰감 있는 / 따뜻한 편집형 / 어두운 기술형 / 선명하고 대담한 / 사진 중심의 고급스러운 / 부드럽고 친근한). 좋아하거나 피하고 싶은 색·사이트가 있나요?
3. **범위와 환경**: 필요한 페이지·핵심 기능·브랜드 자료·모바일 중요도를 알려주세요. 기존 프로젝트가 있으면 현재 기술을 사용할게요.

사용자가 모르겠다고 하면 업종에 맞는 세 방향을 제안한다. 사용자가 자율 진행을 요청했거나 응답 없이 진행하도록 지시했다면 목적에서 합리적인 기본값을 고르고 가정을 명시한다. 필수 API 키나 계정이 없다고 전체 구현을 멈추지 않는다. 로컬 데이터로 핵심 흐름을 만든다.

## 제안 형식

서로 구조가 다른 3개 안을 짧은 비교표로 보여준다.

| 안 | 사용 목적과 맞는 이유 | 화면 구조 | 색·타이포·밀도 | 참고 자료 |
| --- | --- | --- | --- | --- |
| A: 추천 | 핵심 행동에 적합한 이유 | 구체적인 섹션 순서와 열 구성 | 구체적인 방향 | 로컬 이미지와 출처 |
| B | 다른 장점 | A와 다른 구조 | 다른 방향 | 로컬 이미지와 출처 |
| C | 다른 장점 | A·B와 다른 구조 | 다른 방향 | 로컬 이미지와 출처 |

단순히 색만 바꾼 세 안을 제시하지 않는다. 선택 또는 조합 의견을 받고 구현한다. 이미 방향이 지정됐거나 사용자가 판단을 위임했으면 추천안을 적용하고 진행한다.

## 저장할 브리프

`templates/brief.json`을 복사해 `design/brief.json`으로 정리한다. `purpose`, `audience`, `primary_action`, `vibes`, `pages`, `features`, `brand`, `constraints`를 채운다. 답변하지 않은 항목은 확인된 사실처럼 기록하지 말고 `assumptions`에 둔다.

다음으로 `python <skill>/scripts/recommend.py --brief design/brief.json`을 실행한다. 출력에는 스타일 점수의 이유, 구현 구조, 로컬 출처 후보가 포함된다. 점수는 로컬 규칙의 결과이며 객관적인 품질 순위가 아니다.

## 구현으로 넘길 자료

- `design/brief.json`: 사용자 요구와 가정
- `design/ui-proposal.md`: 제안과 선택 방향
- `design/design-spec.md`: 페이지·토큰·반응형·상태·구현할 동작

이 세 파일을 작성하고 실제 코드를 구현한다. 문서만 만들고 완료라고 말하지 않는다. 예제 생성기는 새 프로젝트의 시작점으로 사용하고, 기존 프로젝트는 기존 스택에 맞게 구현한다.
