# Mobbin Site Builder

## 목적

선택한 레퍼런스의 레이아웃, 시각적 위계, 정보 밀도, 인터랙션을 파악하고 사용자의 서비스에 맞는 동작하는 사이트로 구현한다. 추상적인 스타일 설명만으로 모든 사이트를 같은 구성으로 만들지 않는다.

## 1. 입력과 환경 확인

- Mobbin을 요청받으면 먼저 [mobbin-mcp.md](references/mobbin-mcp.md)를 따라 연결된 MCP로 검색한다. 사용자에게 수동 캡처를 요구하는 것은 도구 접근 실패 후의 대안이다.

- 프로젝트의 `AGENTS.md`, 기존 프레임워크, 컴포넌트, 실행 명령을 먼저 확인한다. 기존 스택을 우선 사용한다.
- 사용자에게 받은 스크린샷, Mobbin URL, 공개 사이트 URL, 사이트 명세를 찾는다. 제공된 이미지는 반드시 직접 확인한다.
- Mobbin URL만 있고 접근할 수 없으면 접근 실패를 알리고 필요한 화면 캡처를 요청한다. 공개 사이트를 확인할 수 있다면 그 자료로 계속 작업하되 출처를 구분한다.
- 레퍼런스가 전혀 없으면 사이트 유형과 사용자 목적을 바탕으로 초안을 만들 수 있지만, 특정 Mobbin 사이트를 분석했다고 말하지 않는다.
- 브랜드, 필요한 페이지, 핵심 사용자 행동을 기존 대화에서 파악한다. 결과를 크게 바꾸는 정보만 질문하고 독립적인 작업은 진행한다.
- 새 프로젝트에 스택 지정이 없으면 React + TypeScript + Vite를 기본으로 선택한다. 검색 노출이나 서버 렌더링 요구가 있으면 적합한 프레임워크를 선택한다.

## 라이브러리에서 필요한 사이트 선택

1. [전체 사이트·패턴 인덱스](references/library-index.md)에서 유형과 이름으로 후보를 찾는다. 모든 사이트 문서를 한꺼번에 읽지 않는다.
2. 해당 후보의 사이트별 명세와 [패턴별 구현 플레이북](references/playbooks.md)을 읽는다.
3. 자료가 부족하면 [라이브러리 확장](references/expansion-workflow.md) 절차로 새 사이트·추가 화면·모바일·흐름을 수집한다. 현재 인덱스의 사이트에만 제한하지 않는다.
4. `needs-review` 또는 `usable: false` 자료를 주요 레퍼런스로 자동 선택하지 않는다.
5. 여러 자료를 조합할 때 레이아웃을 맡을 주 레퍼런스와 각 보조 패턴의 출처를 명세에 기록한다.

저장소에서는 `python scripts/search_library.py "검색어"`, `--tag pricing`, `--kind flow`로 검색할 수 있다. 설치된 스킬만 있는 환경에서는 `rg`로 `references/library.json`과 인덱스를 검색한다.

## 2. 구현 전 레퍼런스 명세 작성

다음을 관찰과 추정으로 구분해 기록한다. 기존 사이트 명세가 있으면 보완한다.

1. 화면 목록과 순서: 시작 화면 → 사용자 행동 → 다음 화면.
2. 구조: 전체 폭, 콘텐츠 최대 폭, 열 수, 내비게이션 위치, 섹션 순서.
3. 시각 요소: 배경·텍스트·강조 색상, 폰트 계층, 여백, 모서리, 테두리, 그림자.
4. 콘텐츠: 제목 길이, 카드 수, 이미지 비율, 표의 열 수, 가격 및 메타정보의 위치.
5. 상태: 기본, 로딩, 빈 결과, 오류, 선택, 완료.
6. 반응형: 모바일 캡처가 있으면 실제 차이를 따른다. 없으면 합리적인 축소 규칙을 추정으로 기록한다.

여러 레퍼런스를 조합할 때 하나를 주 레이아웃으로 정하고 나머지는 특정 컴포넌트나 흐름에 연결한다. 어느 부분에서 어떤 자료를 참고했는지 기록한다.

사이트 유형에 맞는 초기 구조는 [site-types.md](references/site-types.md)를 참고한다. 이 문서의 기본값보다 실제 레퍼런스와 사용자 요구가 우선한다.

## 3. 구현

- 전체 실루엣과 주요 영역 비율을 먼저 맞추고 타이포그래피, 간격, 세부 컴포넌트를 조정한다.
- 관찰한 색상, 간격, 글자 크기, 반경을 CSS 변수 등 디자인 토큰으로 정리한다.
- 반복되는 카드, 입력, 버튼, 내비게이션을 컴포넌트로 만들되 일회성 UI를 불필요하게 추상화하지 않는다.
- 사용자 브랜드와 목적에 맞는 구체적인 문구·데이터를 사용한다. 임시 이미지와 데이터는 표시하고 원본 에셋의 확보 여부를 알린다.
- 검색, 필터, 탭, 정렬, 모달, 폼, 페이지 이동 등 화면에 드러난 주요 행동을 구현한다.
- 백엔드가 없으면 일관된 로컬 데모 데이터로 흐름을 완성한다. 결제·예약·계정 생성은 실제 처리로 오해되지 않게 데모 완료 화면에서 명확히 표시한다.
- 링크와 버튼의 의미를 구분하고 레이블, 키보드 포커스, 폼 오류, 모달 닫기, 이미지 대체 텍스트를 구현한다.
- 작은 화면에서는 열과 내비게이션을 재배치하고 가로 넘침을 제거한다. 모션은 reduced-motion 설정을 따른다.

## 4. 검증 및 수정

[quality-checklist.md](references/quality-checklist.md)에 따라 검증한다.

- 프로젝트가 정한 빌드·타입·린트 명령을 실행하고 관련 오류를 해결한다.
- 브라우저 도구가 있으면 레퍼런스와 같은 뷰포트에서 캡처해 비교하고, 주요 사용자 흐름을 실제로 조작한다.
- 비교는 전체 레이아웃 → 글자와 간격 → 색상과 이미지 → 세부 장식 순으로 한다.
- 모바일 캡처가 없으면 최소 375px와 데스크톱 폭에서 확인한다.
- 브라우저 검증을 수행할 도구가 없으면 수행하지 못한 검증을 정확히 밝힌다.
- 검증 중 문제가 발견되면 수정하고 영향을 받은 확인만 반복한다.

## 5. 결과 전달

구현한 화면과 동작, 실행 방법, 검증 결과, 남은 제약을 간결히 설명한다. 실제로 확인한 출처와 추정한 부분을 구분한다. 배포는 사용자의 요청 범위에 따라 진행한다.
